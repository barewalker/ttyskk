# ファンクションキーが子に届かない件 — 調べた記録

**結論: ttyskk は F キーを消していなかった。** 実機で測ったところ F3 は届いており、
届かない F1・F2・F4 は herdr が食っている (ttyskk の外の話)。**ttyskk 側でやること
は無い**ので、調査はここで畳む。素通しは `tests/function_keys.rs` で見張る。

以下は当初の指示書に、実際に測った結果を書き足したもの。同じ症状が再び出たときの
調べ方としてそのまま使える。

## 分かっていること

環境はこの入れ子になっている。

```
kitty  →  herdr  →  ttyskk  →  nvim
```

切り分けた結果:

| 試した形 | F1 | F2 | F3 | F5 F6 |
|---|---|---|---|---|
| 素の kitty (herdr も ttyskk も無し) | 届く | 届く | 届く | 届く |
| kitty + herdr | **届かない** | **届かない** | 届く | 届く |
| kitty + herdr + ttyskk | 届かない | 届かない | **届かない** | 届く |

**F1 と F2 は herdr が食っている。** これは ttyskk の問題ではないので、この調査の対象外。

**F3 だけが ttyskk を足したときに消える。** これが調べる対象。

確かめ方は nvim 側でこうした。貼ってから F1〜F12 を押すと、届いたキーだけ通知が出る。

```
:lua for i=1,12 do vim.keymap.set({"n","t"}, "<F"..i..">", function() vim.notify("F"..i.." 到達") end) end
```

## コードを読んだ限りでは素通しに見える

`src/input.rs` の `parse_escape`。SS3 (`ESC O …`) は 3 バイトまとめて `Key::Raw` にする。

```rust
b'O' => {
    if buf.len() < 3 {
        return (0, Key::Esc);
    }
    (3, Key::Raw(buf[..3].to_vec()))
}
```

`Key::Raw` は子にそのまま渡る経路がある (`skk.rs` の `to_child`)。F1〜F4 はいずれも
`ESC O P/Q/R/S` の 3 バイトなので、**この経路だけを見れば F3 が消える理由は無い。**
つまり読みだけでは分からない。実測が要る。

## 疑っている二つの筋

### 1. そもそも SS3 で来ていない

nvim は起動時に拡張鍵盤プロトコル (`CSI > 1 u`、kitty) や `modifyOtherKeys` を有効に
する。その下ではファンクションキーも SS3 ではなく CSI 系の形で届く。すると
`parse_escape` は `b'['` の分岐に入り、`decode_extended_key(seq, bound)` を通る。

ここが怪しい。`decode_extended_key` は **`bound` に挙がったキー、つまり設定で SKK に
割り当てられているキーだけ**を素の形に戻す作りになっている。戻した結果が SKK の
割り当てと一致すると、ttyskk がそのキーを**消費してしまう**。

利用者の `~/.config/ttyskk/config.toml` にファンクションキーの割り当ては無い。だが
**CSI-u に戻した結果が別の割り当てと衝突していないか**を確かめる価値はある。

### 2. 分割して届いたとき

`parse_escape` は 3 バイト揃わないと `(0, Key::Esc)` を返す。呼び出し側がこれを
「まだ足りない」と解釈して**次の読み込みを待って結合し直しているか**、それとも
捨てているかを確かめる。エスケープ列が読み込みの境界で割れるのは普通に起きる。

## 測り方

**trace を使う。** ttyskk には既に仕組みがある。環境変数にパスを入れると、そこへ追記
される (`src/main.rs` の `Trace::new`)。

```sh
TTYSKK_DEBUG=/tmp/ttyskk.log ttyskk -- nvim
```

**入ってきたバイト・切り出した結果・出て行ったバイトを記録するようにした** (済)。
16 進で出す (`hex`) ので、`ESC O R` と `ESC [ R` の区別が付く。F3 を押すとこう並ぶ。

```
端末→ttyskk 3 バイト 1b 4f 52 (␛OR)
  切り出し 1 個 [Raw([27, 79, 82])]
  ttyskk→子 3 バイト 1b 4f 52 (␛OR)
```

位置報告を抜いたときも記録が出る (`位置報告を抜いた (r,c) 残り …`)。**F3 が位置報告
として食われているなら、ここに出て子へは出ない。**

F3 のとき、**入ってきているのに出て行かない**のか、**入ってくる形が違う**のか、
**そもそも入ってこない** (= herdr が食っている) のかが、これで分かれる。

### 対照実験

同じ手順を三通りでやり、記録を突き合わせる。

1. **素の kitty + ttyskk** (herdr を挟まない) — herdr を容疑から外す。
2. **kitty + herdr + ttyskk** — 実際に困っている形。
3. 子を nvim ではなく `cat -v` にする — 拡張鍵盤プロトコルを有効にしない子なので、
   1. の筋 (SS3 か CSI-u か) が切り分けられる。

`cat -v` なら `ESC O R` は `^[OR` と表示される。**擬似端末が要るので、パイプで流し込む
のではなく実際の端末で対話的に叩くこと** (`script` に標準入力を流し込む形では測れな
かった)。

### 押すキー

F1 から F12 まで順に。F1 と F2 は herdr の下では届かないので、1. の素の kitty での
記録と比べる材料になる。

## 直すときの原則

**割り当てに無いキーは、来た形のまま子へ渡す。** `decode_extended_key` の説明に既に
そう書いてある ―― 「他のキーを素の形に直してしまうと、子アプリが期待する元の形を
壊してしまうため、そのまま渡す」。F3 が消えているなら、この原則がどこかで破れている。

直したら **F1〜F12 が素通しされることを試験で固定する**。`tests/` に既にある
`ctrl_h.rs` が、擬似端末を立てて特定のキーの通り方を見る形になっているので、それに
倣うのが早い。

## やらないこと

- **herdr の F1・F2 は追わない。** ttyskk の外の話。
- **nvim 側の回避は済んでいる。** fzf-lua のヘルプは `<F1>` が既定だが、herdr の下では
  届かないので `<C-/>` `<C-_>` `<C-g>` を足してある (dotfiles の
  `dot_config/nvim/lua/plugins/fzf-lua.lua`)。この調査が済んでも戻す必要はない ――
  Fn 同時押しの要るキーを常用の口にしない、という判断は別に成り立つ。

## 実機で測った結果 (これで畳んだ)

herdr のペインの中で `env -u TTYSKK_ACTIVE TTYSKK_DEBUG=… ttyskk -- nvim` を起こし、
F1〜F12 を順に押して記録を取った (ttyskk が二重になる形)。

```
端末→ttyskk 5 バイト 1b 5b 31 33 7e (␛[13~)     ← F3 が届いた
  切り出し 1 個 [Raw([27, 91, 49, 51, 126])]      ← Raw として切り出した
  ttyskk→子 5 バイト 1b 5b 31 33 7e (␛[13~)      ← そのまま子へ渡した
子 1389 バイト → 控え … ╭ …                      ← nvim が浮き窓を描いた = 反応した
```

- **F3・F5〜F12 は届き、一バイトも変えずに子へ渡り、nvim が反応した**。F キーごとに
  直後 1,300〜1,500 バイトの描画 (`vim.notify` の浮き窓) が続いている
- **F1・F2・F4 はそもそも ttyskk に入ってこない。** herdr が食っている
- **来る形は `CSI 13 ~`** だった。nvim が拡張鍵盤プロトコル (`CSI > 3 u`) を頼むため。
  kitty の terminfo が言う素の形 (`kf3=\EOR`) ではない

**「`CSI 1 ; 1 R` が位置報告として食われる」という筋は外れ。** 実際に来た形は
`CSI 13 ~` で、位置報告とは似ていない。ただし **xterm 系は修飾つき F3 を
`CSI 1 ; 2 R` で送る**ので、この形は原理的に位置報告と見分けが付かない。位置報告を
待っている間 (画面サイズ変更から入力が 3 秒途切れるまで) に限り食われうる。kitty は
この形を使わないので手元では起きない。**直すなら見分ける手立てが要る**が、いまは
起きていないので追わない。

## 一次調査で分かったこと

**ttyskk 単体は F キーを消さない。** `tests/function_keys.rs` で擬似端末を立て、17 通り
の形を ASCII モードとかなモードの両方で流し込み、`cat -v` を子にして受け取りを見た。
全部そのまま届いた。試験を空回りさせていないことは、`ESC O R` だけ別の形に差し替えて
落ちることで確かめてある。

| 形 | 例 | 結果 |
|---|---|---|
| SS3 | `ESC O P`〜`ESC O S` (F1〜F4) | 素通し |
| CSI 文字 | `ESC [ P`〜`ESC [ S` (拡張鍵盤プロトコル下の F1〜F4) | 素通し |
| CSI 数値 `~` | `ESC [ 15 ~`〜`ESC [ 24 ~` (F5〜F12) | 素通し |
| 修飾付き | `ESC [ 1 ; 5 R` (C-F3) | 素通し |

**疑っていた二つの筋は、読みでも実測でも外れた。**

- `decode_extended_key` は終端が `u` か `~` のときしか働かない (`src/input.rs:221`)。
  F3 の `R` は対象外なので、割り当てとの衝突は起こりようがない
- 位置報告の読み取りは `CSI` + 数字 + `;` + 数字 + `R` を要求する
  (`parse_cursor_report`)。`ESC O R` は `CSI` で始まらず、`ESC [ R` は数字が無いので、
  どちらも食われない。**`awaiting_report` が立ちっぱなしでも同じ**
- 切り出しは足りないぶんを持ち越す作りになっていて (`Decoder::feed` の `partial`)、
  読み込みの境界で割れても捨てない

**残る筋は「ttyskk 単体では起きない」もの。** 次に測るならこの順。

1. **herdr を挟んだ実機で trace を取る。** 上の三行が並ぶので、入ってこないのか
   出て行かないのかが一目で分かる。**入ってこないなら herdr の側の話**になる
2. **ttyskk が挟まることで F3 の形が変わっていないか。** nvim は起動時に拡張鍵盤
   プロトコルを頼み、その可否を端末に問い合わせる (`CSI ? u`)。この問い合わせと
   応答は ttyskk を通る。応答が届く形や間合いが変われば、nvim が想定する形と端末が
   送る形が食い違い、**キーは届いているのに F3 として読まれない**ということが起きる。
   trace に `1b 4f 52` が出ていて nvim が反応しないなら、この筋
3. **画面サイズ変更のあと。** ttyskk は変更のたびに位置を尋ね直す。多重化器が
   その応答を返さないと `awaiting_report` が立ったままになる。上のとおり F3 は
   食われないが、**この状態が他の副作用を持たないかは未確認**

- `tests/ctrl_h.rs` — 擬似端末を立てて一つのキーの通り方を見る既存の試験。
